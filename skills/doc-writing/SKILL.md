## 文档与报告撰写

目标是产出能让目标读者理解、决策或执行的完整文档，同时保留用户要求的事实、结构、篇幅和体裁。

### 写作方法论

**1. 明确目标受众和用途**
- 技术文档 → 精确、详尽、可复现
- 管理报告 → 结论先行、数据支撑、简洁
- 科普文章 → 通俗易懂、类比说明
- 邮件/提案 → 要点清晰、行动导向

**2. 结构化写作**
- 复杂文档先建立大纲；短文档直接成稿，避免为了流程而流程
- 每个段落一个主题，首句是主题句
- 使用标题层级组织内容（不超过 4 级）
- 使用列表和表格呈现结构化信息

**3. 质量检查**
- 逻辑连贯性：段落之间是否有清晰的过渡
- 信息完整性：读者能否仅凭文档完成任务
- 一致性：术语、格式、编号是否统一
- 简洁性：能否用更少的文字表达同样的意思

### 常用文档结构

**技术报告**
```
1. 摘要（Executive Summary）
2. 背景与目的
3. 方法/过程
4. 结果与发现
5. 分析与讨论
6. 结论与建议
7. 附录
```

**技术方案**
```
1. 问题描述
2. 目标与约束
3. 方案设计（含架构图）
4. 实施计划
5. 风险评估
6. 成本与资源
```

### 工具策略
- 读取用户提供的模板、历史文档和源材料，优先复用现有风格
- 只使用当前真实可用的编辑、检索和格式转换工具
- 时效性或外部事实需要检索；创意措辞不能替代事实依据

### 格式规范
- Markdown：使用标准语法，标题层次清晰
- LaTeX：使用标准包和命令
- DOCX：保持格式一致性
- 引用：使用标准引用格式

### 质量检查
- 检查语法和拼写错误
- 验证逻辑连贯性
- 检查引用准确性
- 确保格式一致性
- 标注不确定的内容

### 输出风格
- 直接给出修改后的文本，不要只描述修改建议
- 用户要求审阅或红线时再标注修改原因或使用 diff；普通起草直接交付成稿
- 不要使用 emoji，保持专业风格
