# EKO 架构收敛工作流

只有预检发现架构重构、新状态权威、公共协议、跨仓重复实现或近义概念时才读取本文件。

## 一、确定问题

1. 在 `echo-agent` 与 `echo-agent-cli` 中列出重复类型、trait、字段、状态、协议和实现路径。
2. 分别证明定义、注册、运行时可达、消费者、交互端投影和已有验证。
3. 写清当前负面影响：行为分歧、双写、错误恢复不一致、功能不对等、公共接口误导或维护成本。
4. 没有具体负面影响时只记录改进建议，不把偏好升级成架构缺陷。

## 二、确定规范权威

1. 判断能力属于通用框架机制、EKO 产品策略还是适配边界。
2. 通用机制优先归入 `echo-agent`；工作区、产品配置、审查/工作树、文件权威和交互端投影留在 EKO。
3. 选择一个最终规范类型、状态权威、协议或执行路径。
4. 适配器只能做无损转换、元数据注入和产品策略，不得拥有第二套调度、状态、重试或终态语义。

## 三、比较方案

关键架构决策先调研 Claude Code、Codex、Cursor、Devin 或相关成熟实现。至少比较：

- 扩展现有规范权威；
- 把重复语义迁移到更合适的已有层；
- 新建能力，仅当两个仓库现有机制都不能表达需求。

每个方案说明复用程度、跨仓接口影响、迁移风险、删除目标、交互端影响、验证方式和回滚边界。推荐方案必须
解释为何其它方案不能同时满足目标和产品定位。

## 四、设计迁移

1. 按框架优先顺序安排依赖：框架通用机制先稳定，EKO 再消费，最后同步官网和上层指针。
2. 每个阶段至少切换一条真实生产路径，不能只新增抽象。
3. 同阶段删除已被取代的旧实现、调用点、序列化字段、投影、测试和文档。
4. 迁移期间只能保留轻薄适配器；剩余重复必须有明确下一阶段和删除条件。
5. 定义失败、取消、并发、恢复、部分副作用和 TUI/GUI/CLI/JSONL/通道/后台功能对等行为。

## 五、验收

- 新旧输入的功能与语义对等有字段级或场景级证据；
- 两个仓库的真实调用方已切换到规范权威；
- 旧实现、第二状态权威和近义术语已删除；
- 双语文档、示例、官网和相关 Skill 已同步；
- Rust、前端、GUI、契约和集成门禁按实际影响明确；
- 首个实际差异形成后继续调用 `semantic-diff`。

涉及新的公共契约、状态权威或多个可行取舍时，先调用 `brainstorm`，再按已确认方案调用 `design` 和 `plan`；
方案与计划闭合后才进入 `build`。不得用临时兼容层代替未完成的架构决策。
