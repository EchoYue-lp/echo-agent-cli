# EKO 编码前预检

目标是让 AI 在写代码前先证明“为什么要改这里、框架是否已有能力、EKO 适配层是否仍然轻薄、各交互端
如何保持对等”。这是开发指导，不是用户交互权限门控或新的 TaskRuntime 状态。

## 预检顺序

1. 记录 `echo-agent` 与 `echo-agent-cli` 的分支、提交标识、未提交状态、生效 `AGENTS.md` 和用户授权范围；保护已有改动。
2. 暂定 `primary_kind`：缺陷修复（`bugfix`）、功能开发（`feature`）、重构（`refactor`）、契约（`contract`）
   或样式（`style`）；独立标记公共契约、文件持久化、生命周期、并发/恢复、外部副作用、跨仓、交互端功能对等、
   未知证据等风险。首个差异产生后只允许升级深度。
3. 按类型、trait、字段、行为、相邻命名和真实调用路径搜索两个仓库；区分定义、注册、可达和已验证。
4. 明确通用框架机制、EKO 产品策略和适配边界。通用能力优先复用框架，EKO 特有的工作区、审查/工作树、
   文件权威和 UI/TUI/CLI 投影留在应用层。
5. 检查 TaskRun/PlanTask/SubagentRun、会话、记忆、插件、Skill、事件和交互端是否已有唯一权威；
   能扩展现有权威时禁止新建平行存储、DAG、状态归约器、DTO 或近义术语。
6. 读取相邻实现确定 Rust/TypeScript 命名、错误处理、UTF-8、禁止崩溃、组件边界、测试和 UI 文案风格；
   不做与当前目标无关的全仓格式化。

## 输出合同

在写代码前给出：变更分类与风险、已有复用点、框架/应用/适配边界结论、唯一状态权威、允许修改范围、
明确不触碰范围、旧路径删除目标、TUI/GUI/CLI/通道/后台影响、文档/示例/官网/SDK 影响和验证矩阵。

新的架构、状态权威、公共协议或真实产品取舍先进入设计/人工裁决；事实已清楚的局部改动直接实施。预检结果是
任务内工作合同，不成为第二份长期语义材料。

## 阶段衔接

1. 普通局部改动在预检通过后进入编码。
2. 架构重构、新状态权威、公共协议或重复实现收敛先读取
   [架构收敛工作流](workflows/architecture-convergence.md)，完成方案与迁移门禁后再编码。
3. 首个实际代码差异形成后，已有 `semantic/` 基线时调用 `semantic-diff`，重新确认风险和最终验证矩阵；
   尚未建基线时只完成任务内局部语义影响检查并明确该缺口，不伪造对象，也不阻塞普通局部改动。用户目标包含
   建立基线时再调用 `semantic-discover`。风险深度只能升级。
4. 执行测试、静态检查、类型、契约和集成验证。任何失败都先定位根因，不能跳过。
5. 只有 `semantic-diff` 产生高风险失效单元、残余风险、新问题或事故关联时，才调用 `semantic-audit`。
6. 语义材料被创建、更新或问题记录需要关闭时调用 `semantic-verify`，然后才能进入完成声明和仓库提交门禁。

维护这些 Skill 的触发描述时，读取 [路由走查样例](references/routing-cases.md) 并逐项确认应触发与不应触发项。
