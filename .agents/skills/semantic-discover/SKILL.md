# EKO 语义基线发现

把 EKO 当前源码、框架契约、测试、设计和用户可见投影整理成可追踪的语义地图。先发现事实，再决定
是否需要新边界或新接口；不要因为某个交互端暂时没有接入就把能力当成“不需要”。

## 预检

- 首次创建或更新语义对象前调用 `semantic-contract`，取得当前合同版本和对象字段；合同不可用时停止写入。
- 读取两个仓库各自生效的 `AGENTS.md`、当前提交标识、未提交状态和已有 `semantic/` 材料。
- 搜索 `echo-agent` 与 `echo-agent-cli` 中已有能力、规则、公共接口、实现、测试和文档；明确
  通用机制、EKO 产品策略与适配边界。
- 追踪 TUI、GUI、CLI/JSONL、通道、定时/后台任务、启动与恢复等入口，以及状态、持久化、外部副作用和
  用户投影；不要只从 UI 点击路径开始。

## 输出

返回源码快照、区域分类、边界/能力图候选、行为承诺/规则/证据/问题记录候选、交互端功能对等缺口和待审集合。
需要独立探索时优先派发 `semantic-boundary-explorer`，需要能力闭合复核时派发
`semantic-capability-reviewer`。宿主不能发现专用角色时，改用现有只读 `explorer` 或 `reviewer`，并在派发任务中
完整提供两个仓库绝对路径、源码版本、范围、相关对象和输出合同；无法取得独立上下文时由主 Agent 原地只读执行，
并明确缺少独立复核。只有所有相关路径、场景、边界归属和引用都有依据时，才报告两层闭合为 `closed`。
长期材料由主 Agent 写入，探索 Subagent 只返回候选结果。不要新建第二个 TaskRuntime、Todo 存储、DAG 或产品并发权威。

两层闭合与结构检查完成后调用 `semantic-verify`。该调用只验证基线材料，不自动进入代码修改。
