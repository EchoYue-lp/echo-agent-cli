# EKO 语义增量分析

把代码差异变成可执行的影响闭包。记录两个仓库的基准/目标提交和未提交状态；不要把本地未提交变化
误当成已交付事实。

## 分析重点

1. 调用 `semantic-contract`，取得当前合同版本；合同或基线不存在时转入 `semantic-discover`，不能继续增量写入。
2. 通过路径、符号、公共契约、序列化字段和调用关系定位受影响的能力图、边界、行为承诺、规则与证据。
3. 沿框架/应用/适配关系、共享状态权威、TaskRun 生命周期、外部副作用和 TUI/GUI/CLI/通道
   投影扩展影响闭包。
4. 检查 `echo-agent`、`echo-agent-cli`、示例、双语文档和 `echo-website` 的同步影响；需要时分别记录
   `SDK-Docs-Impact`、`SDK-Skill-Impact` 和官网影响。
5. 只将真正受影响的审查单元标记为 `stale`。无法映射的重要变化必须进入局部 `semantic-discover`，不能静默通过。

输出语义变化、影响对象、失效视角、未映射变化和最终验证矩阵。保留人的期望；修复问题记录使用独立的
调试/构建流程，不在本 Skill 中创建第二套差异、任务或状态实现。

输出验证矩阵后先执行对应机器验证。只有存在高风险失效单元、残余风险、新问题或事故关联时才调用
`semantic-audit`；其余情况直接调用 `semantic-verify` 检查本次材料更新。
