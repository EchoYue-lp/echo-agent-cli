The established pattern is already present locally: cancellation signals and retained tasks/receipts are separate; caller loss does not abort accepted work. This design reuses the existing Tokio cancellation, JoinSet/oneshot/watch and receipt registry. It does not introduce an executor or background task solely to keep uncertainty alive.

## 设计

### Physical owner and public observation

The registered TaskRuntime driver invokes the existing `RuntimeTaskService::execute_to_settlement` on its original execution owner. It does not use bounded `execute` as its completion receipt. Public observers may return the typed observation while that registered owner and its original resource receipts remain held. Repeated cancellation never starts another execution or resets the framework deadline.

Normal BackgroundSubagentHandle.join continues to mean the original physical result. Team/framework-created producers drain the original stream to real EOF before surfacing an observation; EKO does not re-drive them. A foreign Agent setup may return observation without supplying any stream/join handle. That is unknown authority, not physical completion.

### Typed adapter results

Preserve the exact nonterminal ReactError through every internal decision that could settle a claim, create a TurnReceipt, finalize a run, release a pool lease or enqueue a retry. Existing private result/error carriers may gain a typed observation branch or carry the original error; no public Task status is invented. Surface text conversion is permitted only after the decision to avoid terminal projection and resource release.

`resolve_dispatch` propagates observation before terminal classification or resolution metadata. It must not use None/status fallback to Failed, nor retry/requeue it. Ordinary AgentFailure category/kind/retryable/message/usage behavior stays unchanged.

Shared foreground and continuation are part of the same error chain. Their current bare TurnOutcome and String-to-Failed fallbacks are not valid observation carriers. The necessary Rust source migration makes the shared foreground result fallible and carries the typed original observation through the last decision to emit a terminal. TUI/GUI/CLI/channel callers use only their existing error presentation for an unsettled observation: they must not publish ChatCompleted, settle ingress as failed/cancelled, clear busy/active generation, release original pool/memory/workspace receipts or schedule continuation replay. This changes no UI/event wire fields and introduces no surface-specific authority. The existing foreground entry retains an explicit observation; dropping its borrowed lease cannot invoke the old Cancelled settlement fallback. Shutdown reports that unknown entry and keeps its original receipts. Normal terminal outcomes continue through the same original observer/projector settlement.

The shared chat driver unwraps only a real successful framework TurnReceipt. Observation bypasses String-to-failed receipt construction and `finalize_run_turn`; neither input-observer projection nor sink cleanup may convert it into a successful, cancelled or failed receipt. All surface-specific presentation continues using the existing event shape.

### Unknown resources in the existing registry

If the registered future returns a typed observation without a physical receipt/source, the existing RunDriverSupervisor retains the original driver token, run/execution identity, cancellation registration, generation lease, memory/pool receipts and context binding in an internal uncertainty record. It reports the typed observation to the caller without spawning a never-ending future. This record is distinct from `RunSettlementDebt`: that debt retries a known terminal write and contains a target status, which is not valid evidence here.

Admission checks the existing supervisor uncertainty records atomically with normal active driver admission. A retained unknown run/generation cannot be executed again, rebound, or treated as idle. Existing queries and shutdown reporting expose uncertainty as an error/diagnostic using existing result shapes. Shutdown must not clear the record or release its resources just because other tasks ended or cleanup was retried.

Release requires actual evidence linked to the same identity: the original owner/background receipt has physically settled, or an explicitly authorized process termination has been observed. Cancellation submission, elapsed time, caller disappearance, a fresh execution, process restart, or in-memory record disappearance are not evidence. No new recovery/reset command is introduced. If the original foreign Agent provides no completion evidence, the registry remains an explicit uncertainty fence; this is not replaced with a fabricated Failed debt.

Restart must not infer physical termination from loss of an in-memory fence. The existing FileTaskShadow journal carries an exact owner intent before accepted work can run, using the existing run/execution/generation/driver receipt identity and existing recovery-blocker/event authority. Observation retains that intent; only same-owner physical terminal evidence clears it in the existing journal. An append/write failure rejects before execution or releases no admitted resource. Original TaskRun recovery, boot auto-resume, resume/retry and driver admission must inspect that same unresolved fence before clearing a claim, changing a status, starting work or publishing a new workspace generation. The fence does not create a new Task status or journal, nor does it block all historical Running tasks: only the exact unresolved intent is protected. Existing ordinary recovery behavior remains for tasks with genuine settlement evidence or no protected intent.

The current `recover_interrupted_run` and `boot_auto_resume_decision` are not already sufficient: their old behavior can clear Running ownership or permit replay. This migration explicitly adds their check of the retained canonical fence. Normal terminal settlement atomically acknowledges the matching intent in the existing journal. Wrong identity/generation and stale completion cannot clear it. No generic Retry/ResolveRecovery UI decision is silently treated as physical evidence. Source APIs that publish actual process death may clear only the exact owned intent with that evidence; absent such a source, uncertainty stays visible and blocks automatic execution.

### Analysis resources

Analysis terminal classification becomes fallible before `settle_analysis_run` writes any latest-run or immutable terminal record. On observation, retain the original accepted AgentPool execution receipt and product-data/cancellation scope in its existing owning registry, keyed by the same analysis/run identity. Do not merely keep the file state while dropping the lease in `run_analysis_with_product_data`.

Reuse the existing `AnalysisRunSupervisor` / `AnalysisRunEntry` and pool admission. Its entries currently exist only in memory and its result is stringified before Joined; this migration adds a minimum private typed uncertainty/receipt slot to that same entry, not another supervisor.

A private owner-fence file in the existing analysis directory holds only the original analysis/run/execution/generation/owner receipt facts needed to reject duplicate work. Persist the intent through the existing analysis `write_json`/framework `atomic_write` path before accepted execution and before `clear_generated_outputs`; read and validate it under the same analysis admission on startup/start/save/delete. A malformed or failed write is an explicit error before side effects. Merely receiving observation and then writing the file is insufficient because it leaves a crash gap. The same accepted entry retains pool execution, product-data flow and cancellation/control scope on observation; its monitor, poll, wait, cancel and shutdown must neither mark Joined nor remove the entry/settle the flow because that observation returned.

Clear the private intent only after a real original-owner completion (or confirmed authorized termination of that exact owned process), matching every retained identity. Record the normal terminal result durably before clearing; if clearing fails, keep the original receipt and report cleanup failure, with identity-safe retry requiring no re-execution. A crash between terminal write and fence clear is resolved only by the matching durable terminal evidence. If there is no physical receipt, including foreign setup uncertainty, the restart read refuses new analysis execution and output clearing; it does not infer the original work stopped because the application process changed. The late-evidence input is the original entry's physical result/owned process receipt, never a new execution or synthesized result. This adds no public analysis status, second journal/store or automatic recovery command. Ordinary output capture and record shape remain unchanged; GUI IPC may present an existing error but must not emit a terminal analysis result.

The existing cron FireFn is another direct registered TaskRun caller, not a new scheduler policy. It uses the same typed registration and receipt transfer before model/tool effects; preserve an executor observation through the original supervisor and existing ReactError boundary. Ordinary cron error context stays unchanged. TUI/GUI retry transfer the same pre-acquired pool and memory receipts instead of leaving a pool lease in a returning observer future; original receipt ordering releases pool before memory. No cron retry, schedule, public status or automatic execution policy changes.

Current upstream integration is explicitly not closed by that adapter alone: the public intermediate framework f0a6cd1 SchedulerRunner still maps every callback Err to a failed terminal occurrence/last-run projection and drops its CallbackOwnerGuard, while cancellation requeues OutcomeUnknown. Returning typed observation must not permit that enclosing authority to invent physical completion or replay the same admitted effect. Root was given the exact original scheduler path for the framework owner to adapt its existing occurrence journal/admission; C adds no second scheduler, fake pending future or compensating state. This dependency remains required before cron end-to-end acceptance.

### Original SchedulerHandle slot and lifecycle re-observation

This is a bounded integration of the already accepted B ownership boundary. The saved development checkpoint used the clean public intermediate framework f0a6cd1. Root subsequently fixed the same clean sibling to the public development checkpoint 3dedb9a6834cd28a3718d9852023722a6d24f4dc through unchanged canonical relative paths. It provides `SchedulerHandle::join(&mut self)` / `shutdown(&mut self)`, retaining the original Runner and same optional loop JoinHandle. This is not final framework-main consumer qualification; do not borrow dirty framework paths or imply that the earlier focused tests covered this integration. A receiver compile failure is not the behavioral counterexample.

Reuse only `SchedulerState.handle: tokio::sync::Mutex<Option<SchedulerHandle>>` in `state/config.rs`, and `ApplicationLifecycleOwner::join_owned` in `runtime.rs`. Shutdown locks that same slot, borrows `as_mut()` through the original `shutdown().await`, and removes the handle only after `Ok(())`. Every `Err`, including typed Unknown and an ordinary join error without affirmative completion, keeps the same handle; neither string matching nor `is_finished()` is a physical callback receipt. A second caller serializes on this mutex and re-observes the original handle after the first returns. Dropping a borrowed shutdown wait before loop completion releases the mutex guard but leaves the original JoinHandle/Runner in the slot; no abort, replacement spawn, new runner, cancellation token or journal is introduced. An empty slot is successful only when no scheduler was started or this same slot was already cleared after genuine success. Bootstrap's exclusive `&mut AppState` installs it once; shutdown does not replace an application generation.

The strong root remains `Runtime/Services/Settlement/typed ApplicationLifecycleError receipt -> original lifecycle retention -> original Owner -> AppState -> SchedulerState -> same Handle -> original Runner`. The AppState already has its operational Runner Arc; that does not replace the lost JoinHandle or make a second close of an emptied slot valid. No new Root backedge, scheduler registry, publication channel or public status is added.

Move the existing scheduler shutdown observation outside the one-time `normal_drained` block, retaining its cleanup order before pool/primary Agent dependency teardown. On every real original lifecycle poll, `Err` is recorded with the existing retained diagnostic and contributes to that poll's `uncertain` decision. Other independent normal cleanup still runs. The same Owner is restored in the existing Root, and primary Agent/plugin/workspace dependencies must remain reachable. A later original poll must revisit the same handle even when `normal_drained` is already true; only successful scheduler observation removes this particular uncertainty. Previous diagnostic failures remain truthful history and need not be erased to claim physical completion. There is no public scheduler progress watcher in the confirmed upstream API: an existing original driver progress notification or an explicit re-observation of the same Settlement can request another poll. Do not promise autonomous recovery if no genuine late receipt/progress source exists, synthesize a final result from local EOF, or re-invoke FireFn to obtain evidence.

The first compilation failure (two fixture API errors) is preserved separately and is not the behavior-before. After-validation of the source fix remains pending. The slot case admits one actual framework occurrence and holds its callback resource: the original implementation must demonstrate loss of the slot/parent or a second false-success observation after the first typed Unknown; the fixed implementation must preserve exact handle/occurrence identity and callback count across repeated and concurrent shutdown, cancelled borrowed waits, and observation with the loop already ended. ### Aggregate shutdown and the original retained root

This bounded aggregate increment was independently design-reviewed with C0/I0/M0 and Root approved implementation. The candidate implements this composition; current aggregate after tests and independent implementation review remain pending. The actual preaggregate regression compiled and failed on the original total pool wait, after its test cleaned up the same backend. The preceding typed/fence decisions remain approved. The current `join_owned` cannot merely report Task/analysis uncertainty and then call the old total `ProductDataIoService::join_shutdown` or `AgentPool::shutdown`: retained original flows/leases make those waits permanent. Nor may it return and drop `ApplicationLifecycleOwner`, because the current settlement watch contains only metadata. Changing only the watch is therefore insufficient.

Reuse the original `ApplicationLifecycleOwner`, `start_join` producer and `ApplicationLifecycleSettlement`. Add the following private Rust composition, without a public Task/Analysis state or wire field:

| Existing location | Private field / carrier | Ownership and purpose |
| --- | --- | --- |
| `runtime.rs` `AgentRuntime` and `ApplicationServices` | `lifecycle_retention: Arc<ApplicationLifecycleRetention>` | The application-generation strong root is created during bootstrap and shared during compose before accepting work. It outlives a consumed Services value. |
| `ApplicationLifecycleRetention` (same module) | `state: Mutex<LifecycleContinuationState>`; metadata-only `publications: watch::Sender<Option<LifecyclePublication>>`; root-owned `driver_resources` | State contains the original `Option<ApplicationLifecycleOwner>`, its next original cleanup phase and metadata-only observation/final result. It does not contain a clone of the public receipt carrying this root. The mutex is never held over an await. |
| `ApplicationLifecycleOwner` | `retention: Weak<ApplicationLifecycleRetention>` | The original owner is placed back in its root only when progress is blocked by exact retained uncertainty. This backedge cannot keep the root alive. |
| `ApplicationLifecycleSettlement` and returned `ApplicationLifecycleReceipt` | private `Arc<ApplicationLifecycleRetention>` continuation when unsettled | An outstanding settlement or returned diagnostic retains the same original owner after `join` consumes Services. Clone/debug/equality keep existing public reason/error/failure semantics; no serialization or UI field is added. |
| `RunDriverReceiptOwner` and original registered driver | `Arc<RunDriverResources>` | This is the existing resource bundle (generation lease, cancellation registration, pool/memory receipts), not a new executor. The real producer holds it while running. |
| The root retention, and original `RunDriverSupervisor` | root strong resource projections; supervisor weak resource indices | Root stores strong handles to those same bundles before accepted work begins; the supervisor keeps exact driver/context/unknown/debt decisions and `Weak<RunDriverResources>` indices. Its resource projection is not an additional admission or task registry. |

`LifecycleContinuationState` uses an original owner/receipt slot, a single-flight polling bit and a progress revision; the Owner records completed cleanup phases. These are private Rust lifecycle bookkeeping, not TaskRun/Analysis statuses. `start_join` still spawns the real owner cleanup, holding a strong root for its duration. The producer drains all ordinary independent work first. When only dependencies on exact unknown resources remain, it stores **the same owner and remaining cleanup phases** in the root, publishes a nonterminal error observation and ends that poll. There is no dummy never-ending task and no boxed future left permanently unpolled. A final receipt is published only after every original cleanup obligation actually settles.

A real original owner/receipt progress notification upgrades the weak root and resumes the stored continuation through the same single-flight `start_join` path. A later call to the same Settlement may also request that progression (including an identity-safe known-terminal cleanup retry); it never executes Agent work. Taking `Option<Owner>` under the root mutex allows only one actual poller. Every attempted poll either finishes, advances an actual cleanup phase, or restores the owner and returns its existing uncertainty; there is no polling loop without a subscribed progress change. Progress revision and taking/restoring the owner use the same mutex; a progress change during a poll causes one resumed poll after metadata publication. Keep the polling claim through publication so an older observation cannot overwrite a later final result. Borrowed waiter drop cannot abort the real producer. Repeat observers can read the current error promptly, but they cannot relabel it a final drain. Without a real late receipt source there is deliberately no autonomous recovery: the root retains the owner, and durable fences reject same-identity work.

The actual headless caller chain is part of the ownership constraint: `src/main.rs` drops `AgentRuntime` after awaiting shutdown (the TUI and ordinary CLI paths), while `src/cli/modes.rs` converts `ApplicationLifecycleReceipt::into_result()` into the existing `ApplicationLifecycleError { receipt }` and uses `anyhow::Error::new`. Preserve that typed error object: its private receipt continuation must keep the root alive after Runtime is dropped. The existing GUI desktop path likewise maps the typed error rather than replacing it with formatted text. Formatting for logging only borrows the error. No AppState, TaskStore, Pool, Agent or subsystem may gain a strong reference to this root; those progress hooks and resource bindings must use Weak. The retained Owner does not contain Runtime or Services. A strong case drops Runtime and Services and retains only this typed error, proves original unknown resources/Task capabilities remain alive, supplies genuine matching proof through the original route, then drops the receipt and verifies Weak deallocation after actual cleanup. This rules out a hidden aggregate cycle or an accidentally stringified continuation.

The root must be attached to the actual TaskRuntimeStore/AppState/workspace composition **before** any registration that can accept work or transfer receipts. An unbound resource-bearing admission fails before effects instead of accepting a bundle with no reachable owner. All existing application surfaces bind the same root through their canonical composition, and focused standalone store fixtures bind an explicit scoped root while exercising the same supervisor. TaskRuntimeStore, Task/Tool services and `ScopedChatRuntime` retain their original strong operational references and complete capabilities. Only the reverse resource index becomes Weak. This is an ownership invariant, not a product permission check or an optional capability switch.

The fixed aggregate source review found four implementation defects, not new product choices. Keep the single-flight claim through both normal and no-runtime publication; borrow the original Owner across cleanup, not additionally dropping a panicked foreign join object or the explicit original Owner/resource bundles, and never repolling that poisoned object while other independent joins still run. An arbitrary external async future may destroy its own internal locals during unwind; catch does not restore those resources or create physical completion evidence. The strong case therefore checks the outer explicit original bundle, pool permits and Agent Weak reachability independently of any particular fixture capture. Any uncaught cleanup unwind publishes retained uncertainty instead of dropping the Owner or leaving observers asleep. Original foreground Entries project typed observation into each exact retained pool receipt (including the GUI's same lease cell), with hooks called outside the Entry resource monitor; an ordinary same-key lease still drains independently. The original analysis supervisor has only a Weak progress link and notifies it after final entry/terminal publication, including known cleanup commit. Earlier resource-release notifications cannot substitute for this later semantic commit. Repeated unchanged observations do not generate progress loops. Strong controlled cases exercise these four original cuts; the analysis monitor case keeps its existing 30-second drain budget unchanged.

### Exact ordinary-work and uncertainty partitions

Product-data partitioning stays inside the original `ProductDataOperationSupervisor`. Replace its anonymous active count with exact private operation IDs in that same state; `ProductDataOperation` owns its existing ID, and `ProductDataIoFlow` identifies its original parent operation. Mark only that exact parent's retained observation with the original analysis/run receipt. Real nested blocking/async operations remain ordinary live work until they actually finish: a retained parent cannot hide an in-flight filesystem write. Admission remains sealed and all active counts/permits remain held. The aggregate wait returns an unsettled error only when no ordinary operation remains; it does not report active=0 or settle the retained flow. Matching physical evidence resumes the same flow cleanup and removes its exact retained identity once.

Pool partitioning stays inside original `AgentPoolAdmission` / `AgentPoolExecutionLease`: assign an exact private lease token at issue and record uncertainty against that token when its original receipt is retained. The framework `KeyedExecutionAdmission` and its actual permit remain the quota authority. New bookkeeping is an observation projection in the same admission, not another semaphore. Ordinary lease drop removes its token; an uncertain token is cleared only by release of that same physically settled lease. The aggregate awaits all non-uncertain original tokens, then reports the exact retained tokens instead of waiting forever or clearing their Agents. Another active lease on the same conversation/key cannot be excluded merely because one lease is uncertain. No `active - guessed_unknown` arithmetic or global “any error means skip pool” is permitted.

`WorkspaceExecutionRuntime::shutdown` follows that same exact partition. It continues real Task/hook/review and ordinary pool cleanup; mutations/close of an Agent, tool set, memory or plugin still required by a retained owner remain in the same continuation. `WorkspaceRuntimeRegistry::shutdown` visits every already-sealed host and does not let one host's nonterminal observation prevent later independent hosts from draining. The aggregate similarly drains ordinary product-data and independently owned services, while keeping dependent Agent/workspace/plugin resources alive. Existing failures still aggregate; uncertainty cannot authorize dropping a dependency to make later cleanup look complete.

### Actual strong/weak reference graph

The intended graph is explicit:

- Normal application roots: `AgentRuntime` / `ApplicationServices` / live Settlement or returned diagnostic -> Strong retention. Retention -> Strong original stored Owner and original resource bundles. Owner -> Strong AppState -> Strong original analysis registry; Owner -> Strong TaskRuntimeStore and Pool. Owner -> Weak retention. Metadata cached in retention never holds a root-bearing receipt, preventing `Receipt -> Root -> Owner -> Receipt`.
- Task resources: TaskRuntimeStore -> original supervisor metadata -> **Weak** resource bundle; real registered producer and application retention -> **Strong** same bundle. Generation/cancellation registrations hold Weak Store links; the original Root/Owner supplies the strong operational Store. Pool/Agent receipts keep their required strong services. Consequently `bundle -> Weak(Store)` and `bundle -> Pool -> Store -> Weak(bundle)` are not strong cycles. `bundle -> AgentHandle -> ToolManager -> ExecuteTaskTool -> Store` also ends in that same Weak index; it does not require weakening Task tool services or losing their store. Transfer of every resource-bearing original driver/tool receipt uses this one bundle before its observer may return. No old strong `execution_receipts`, `tool_receipts` or `uncertain_drivers` resource branch may bypass the projection.
- Analysis: original AppState -> Strong AnalysisRunSupervisor -> Strong original Entry -> original control/pool/flow. Its control may reference Store/Pool, but neither references the analysis supervisor. Keeping the original AppState in the retained Owner therefore retains the actual analysis owner without a cycle or a second analysis registry.
- Workspace opaque guards: change only the lease receipt's lifetime projection. `WorkspaceRuntimeHost.control_lifecycle` becomes `Arc<Mutex<WorkspaceControlLifecycle>>`; `WorkspaceControlReceipt` holds that same counter/control state and immutable identity, **not** `Arc<WorkspaceRuntimeHost>`. Thus Agent/ToolManager -> InvocationResourceGuard -> ScopedWorkspaceIoReceipt -> original control counter has no path back to Host -> execution -> Agent. Full `ScopedChatRuntime` keeps its strong Host/execution/Store/Pool services; only the guard intended to be opaque loses the unrelated host backedge. The same counter still blocks real workspace retirement until the guard is physically released. The full workspace-control lease still strongly owns its Host; only its opaque I/O projection is counter-only. The Task execution resolver holds Weak workspace-registry linkage while the original AppState/root and full scoped control keep the actual registry/Host services alive.

All root ownership transfers happen before publishing observation. Resource slots are not cleared by shutdown begin, an observer result, or dropped waiters. On matching physical proof the original supervisor first completes durable terminal/fence cleanup, then releases the same bundle once and removes its weak index; a stale completion cannot release another generation. When all remaining phases finish, root state drops its Owner/resource projections and publishes final metadata. A process restart consults the original durable fences; disappearance of this in-memory graph is not a physical receipt.

This is the application composition of existing mechanisms. Tokio's [shutdown guidance](https://tokio.rs/tokio/topics/shutdown) separates signalling cancellation from waiting for tracked tasks; the Rust standard library's [Weak ownership model](https://doc.rust-lang.org/std/sync/struct.Weak.html) provides non-owning backedges. These support the implementation mechanics, but do not invent EKO terminal evidence. The existing application ADR0004 remains the aggregate authority; its bilingual text states this narrow observation/continuation distinction. Bootstrap rollback and dropped owning surface futures transfer the original Owner into the same real cleanup producer, including its metadata-only begin receipt; they do not abort/drop accepted ownership. AgentRuntime owner admission is one-shot for this generation, so a repeated compose cannot overwrite a continuation held by an older observer. Known physical completion with failed persistence keeps the exact original resource bundle until same-owner durable cleanup succeeds. Shutdown diagnostics cannot authorize its release, and an older retry cannot replace an already committed terminal result.

## 异常与边界

- Normal successful, cancelled, timed-out and failed physical receipts keep their exact existing fields and effects.
- Observation retains run_id and optional execution_id without string parsing or default failure construction.
- Caller cancellation/drop affects its wait, not the real owner; close/shutdown reports unknown while its evidence is absent.

- A genuine late original-owner receipt may settle once and release exactly that record; wrong identity/generation cannot release it.
